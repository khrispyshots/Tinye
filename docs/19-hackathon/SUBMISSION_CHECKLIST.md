# Submission checklist

**Status:** Draft | **Version:** 0.1 | **Last updated:** 2026-11-14  
**Responsible role:** Product owner / finance / demo lead

## Purpose

Prevent unsupported claims in future event submissions.

## Assumptions and dependencies

This is a documentation proposal, not an implemented or approved product. The master specification and owner approval govern scope. MVP means the proposed testnet release; later features require separate acceptance. Terms and shared states follow the [product requirements](../00-product/PRODUCT_REQUIREMENTS.md).

## Required checks

- [ ] Confirm actual event rules, dates, eligibility, licensing and required submission format from official event sources; no event selected now.
- [ ] Owner accepts public project description, source/asset licences and privacy-safe demo.
- [ ] Clearly state which features are implemented, testnet-only, simulated, unavailable and deferred.
- [ ] Link actual code/build/deployment/receipt evidence only when it exists; no example addresses presented as real.
- [ ] Explain on-chain/off-chain boundary, custody/upgrader powers and security assumptions.
- [ ] State no live yield/merchant/credit claim unless independently implemented and approved.
- [ ] Validate mobile accessibility, safe test accounts and reproducible demonstration.
- [ ] Remove secrets/personal data from video, screenshots, logs and repository.
- [ ] List limitations, legal/security review status and next approved roadmap phase.

## Acceptance

Reviewer verifies each claim against actual artefacts. Documentation completion is not a working-product submission. Event acceptance does not authorise production deployment or real-money service. All implementation evidence boxes are currently unfulfilled.

## Unresolved decisions

See the linked decision register; recommendations are not approvals.
